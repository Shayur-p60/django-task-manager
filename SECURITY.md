# Security policy

## Reporting a vulnerability

Please **don't open a public issue** for security problems. Report them
privately through GitHub: **Security → Report a vulnerability** on this
repository (private vulnerability reporting). Include what you found,
how to reproduce it, and the commit or image digest you tested.

You should get a reply within a week. Fixes are released as a new image
from `main`; the advisory will name the fixed commit.

## Supported versions

Only the latest image built from `main` is supported. Images are tagged
with the full git commit SHA (`ghcr.io/shayur-p60/task-manager:<sha>`);
there are no long-lived release branches.

## What the pipeline guarantees

Every pull request and every push to `main` runs these gates in
[`.github/workflows/ci.yml`](.github/workflows/ci.yml). A failing gate
fails the build; results also go to the repository's **Security → Code
scanning** tab as SARIF.

| Gate | Tool | Fails the build on |
|---|---|---|
| Secrets | gitleaks, full git history | Any finding |
| Code | Semgrep, `p/python` + `p/django` | `ERROR` severity |
| Dependencies | pip-audit | Any known vulnerability in `requirements.txt` (dev-only `requirements-dev.txt` findings are warnings) |
| Infrastructure config | Trivy config on `infra/terraform`, the rendered Helm charts, and the `Dockerfile` | `HIGH` / `CRITICAL` |
| Dockerfile | hadolint | Warnings and errors |
| Image | Trivy, OS + Python packages | `HIGH` / `CRITICAL` **with a fix available** |

A weekly scheduled run repeats the scans against `main` to catch
vulnerabilities published after a merge.

Images pushed from `main` are additionally:

- **built once**: the exact image that was scanned is the one pushed,
  and everything afterwards uses the digest the push returned;
- **signed** with cosign keyless signing (GitHub Actions OIDC, recorded
  in the public Sigstore transparency log);
- **given an SBOM** (SPDX JSON, generated by Syft) attached as a signed
  attestation, and also kept as a workflow artifact;
- **verified** in the same run (`cosign verify` and
  `cosign verify-attestation`) before the job succeeds.

### Verify an image yourself

```bash
IMAGE=ghcr.io/shayur-p60/task-manager@sha256:<digest>

cosign verify "$IMAGE" \
  --certificate-identity https://github.com/Shayur-p60/django-task-manager/.github/workflows/ci.yml@refs/heads/main \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com

cosign verify-attestation "$IMAGE" --type spdxjson \
  --certificate-identity https://github.com/Shayur-p60/django-task-manager/.github/workflows/ci.yml@refs/heads/main \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  | jq -r '.payload' | base64 -d | jq '.predicate.packages | length'
```

The identity check matters: it proves the image was signed by this
repository's `ci.yml` workflow running on `main`, not just by anyone with
a valid Sigstore certificate.

## Pipeline hardening

- **Least privilege:** the workflow token is `contents: read` by default.
  Scan jobs add only `security-events: write` (SARIF upload); only the
  `publish` job gets `packages: write` (GHCR) and `id-token: write`
  (signing).
- **Publishing is restricted:** `publish` runs only for a `push` to
  `refs/heads/main` in `Shayur-p60/django-task-manager`, never for pull
  requests or forks, with a concurrency group so two releases never
  overlap. The workflow never uses `pull_request_target`, so code from a
  fork never runs with secrets or a write token.
- **Pinned dependencies of the pipeline itself:**
  - every GitHub Action is pinned to a full commit SHA;
  - every downloaded tool (gitleaks, Trivy, hadolint, kubeconform, Syft,
    cosign) is pinned by version and SHA-256, checked by
    [`.github/scripts/install-tool.sh`](.github/scripts/install-tool.sh);
  - Semgrep and pip-audit are pinned by version;
  - the Docker base image is pinned by digest.
- **Dependabot** ([`.github/dependabot.yml`](.github/dependabot.yml))
  proposes weekly updates for Python packages, the base image digest and
  the pinned action SHAs.
- `actions/checkout` runs with `persist-credentials: false`, so later
  steps can't reuse the checkout token.

## Known, accepted findings

Suppressions live next to the tool that uses them, each with a reason.

| Where | What | Why |
|---|---|---|
| `tasks/templates/tasks/task_form.html` | `nosemgrep` for `django-no-csrf-token` | False positive: the form does contain `{% csrf_token %}`, but Semgrep's generic-mode pattern only spans a limited number of lines, so it misses the token in longer forms. Confirmed with test templates; `test_task_forms_include_csrf_token` checks every rendered POST form has the token. |
| Image (not gated) | Unfixed vulnerabilities in Debian base packages | No patched package exists yet, so nothing in this repo can fix them. They're excluded from the gate with `--ignore-unfixed` but **reported** in the Security tab, and Dependabot's base-image updates pick up fixes when Debian ships them. |
| Infrastructure config (not gated) | LOW/MEDIUM findings, e.g. no `HEALTHCHECK` in the Dockerfile (Kubernetes and docker compose define their own health checks) and images not from an allow-listed registry (the local k3d registry) | Below the HIGH/CRITICAL threshold; visible in the Security tab. |

`.trivyignore.yaml`, `.gitleaks.toml` and `.hadolint.yaml` currently have
**no** suppressions. Any future Trivy suppression must have a `statement`
and an `expired_at` date about 90 days out.

## Repository settings (manual)

These can't be set from code. Turn them on under **Settings → Code
security** (and **Settings → Branches**):

- Private vulnerability reporting
- Secret scanning and push protection
- Dependabot alerts and Dependabot security updates
- A branch protection rule (or ruleset) on `main` that requires the CI
  checks to pass and requires pull requests
- After the first publish: make the `task-manager` package public under
  **Packages** if others should be able to pull and verify it
